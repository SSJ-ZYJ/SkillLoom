# 文档生命周期与交付

文档的价值取决于读者能否判断它现在是否成立。区分现行事实与历史过程，是让文档可长期维护的前提。

## 现行与过程分离

| 类别              | 位置                                                       | 特征                                     |
| ----------------- | ---------------------------------------------------------- | ---------------------------------------- |
| 现行事实          | `docs/architecture/`、`docs/testing/`、`docs/terminology/` | 无日期，描述当前状态，随能力一起修改     |
| 架构决策          | `docs/adr/`                                                | 编号文件名，记录取舍与后果，状态明确     |
| 过程材料          | `.agents/notes/plans/`、`audits/`、`archives/`             | 文件名以 `YYYY-MM-DD` 开头，写明观测时间 |
| 可复用 Agent 能力 | `.agents/skills/`                                          | 方法与模板，不含带日期的一次性结论       |

`docs/` 不承担过程记录。审计快照、实施计划、验证快照写入 `.agents/notes/`，并按类型分目录。过程材料不替代实时门禁或现行规范。

## 状态标注

文档标题下一行写英文元数据：

- `Status: adopted`：已采用，正文描述当前事实。
- `Status: historical`：已被替代，必须给出替代文档的链接。
- 带日期的计划与审计不写 `Status`，日期本身表明时效。

历史文档不机械删除。有设计依据的记录标注状态并保留，无依据的流水记录直接删除，判断依据是能否从 Git 与现有测试还原。

## 现行文档的写法

- 不写“已实现”“即将支持”“计划中”。能力是否存在由源码、脚本与门禁决定。
- 不写日期与时间。现行事实没有观测时间，只有当前状态。
- 不写变更历史。需要历史时查 Git，需要取舍时查 ADR。
- 一处事实一处维护。同一事实在多个文件出现时，保留唯一维护处，其余改为链接。

## ADR

只在决策具有独立性时新增，不预先建空模板。一页足够，包含四部分：

1. 背景：约束、已排除的方案与原因。
2. 决策：采用什么，用陈述句写。
3. 取舍：放弃了什么，代价是什么。
4. 后果：对代码结构、检查方式与后续决策的影响。

现行实现细节仍写在 `docs/architecture/`，ADR 只记录决策本身。已被推翻的 ADR 标注 `Status: superseded` 并链接新决策。

## 内容分工表

根入口与 `docs/AGENTS.md` 各维护一张表，回答“这个事实以哪份文件为准”。新增专题文档前先登记条目与职责，再写作。表只列文档与职责，不复制文档内容。

判断是否需要新文档：现有文档能容纳该职责时扩展现有文档；职责不同且篇幅会超过 500 行时才拆分。

## 归档

- 失效文档先确认是否仍有设计依据。有依据的标注历史并保留，无依据的删除。
- 同一问题只保留一份过程记录，更新时改日期并追加结论，不为每轮检查新建报告。
- 删除可由 Git 还原的阶段流水记录，例如逐次审查报告、补丁快照、临时清单。
- 归档目录按年份或主题组织，文件名保留原始日期。

## 提交与协作

- 提交信息用 Conventional Commits，类型与格式以组织规范为准。
- 测试与实现同笔提交，不单独拆测试提交。
- AI 实质性参与按组织规范在 PR 中披露。
- 只有明确要求才执行 commit、push、rebase 或修改历史。不清理工作区，不覆盖他人改动。
- 多 Agent 并行时先按模块划分文件所有权，不相互覆盖。

## 交付报告

完成改动后给出六项，缺项即视为未完成：

1. 修改原因与根因。
2. 改动的文件清单，每个文件一句话说明变化。
3. 实际执行的验证命令与结果。
4. 失败项与失败原因。
5. 未覆盖范围与风险。
6. 需要用户决定的事项。

“已修复”“应该没问题”不属于验证结果。构建成功或进程启动不能替代页面可用性。

## 部分暂存的验证

只提交部分改动时，完整工作区通过不能证明该切片独立成立。隔离验证的做法：用基准提交加候选文件在独立目录重建，再在目录内运行检查。记录基准提交、候选文件、检查方式与未覆盖项。

## 落地示例

- 文档写作规则：`docs/AGENTS.md`。
- 内容分工表：根 `AGENTS.md` 的事实依据表与 `docs/AGENTS.md` 的内容分工表。
- 决策记录：`docs/adr/` 下按编号命名的决策文档。
- 过程材料：`.agents/notes/plans/`、`.agents/notes/audits/`、`.agents/notes/archives/`。
- 协作规范：所属组织的协作规范文档。
