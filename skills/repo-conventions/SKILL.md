# 仓库规范维护

仓库规范方法，适用于任意仓库。规范的目标不是文档齐全，而是让每次改动都能回答三个问题：依据在哪、边界在哪、怎么验证。

下文出现的目录名与命令名是推荐约定。接入已有仓库时按实际命名调整，规则本身不变。

## 何时使用

- 新增、拆分或审查任意 `AGENTS.md`。
- 引入新概念、译名或禁用词，或核对文档用词。
- 新增检查脚本、规模阈值、阈值例外或 CI 门禁。
- 新增、移动测试文件，或调整测试层级。
- 判断一段内容该进 `docs/`、`content/` 还是过程材料目录。
- 在另一个仓库建立同一套规范。

## 六条核心原则

1. **一处事实一处维护。** 已有维护处的事实只链接，不复制。复制即产生第二个状态源。
2. **分层入口，就近读取。** 根 `AGENTS.md` 只放跨目录约束、入口和验证矩阵。目录级信息写在该目录的 `AGENTS.md`。改哪类文件读哪份文件，不整仓加载。
3. **强制程度显式。** 未标注的条文一律强制。`SHOULD` 表示需要审查说明理由，`MAY` 表示可选。加粗与“必须”只留给改变行为的分句。
4. **能机械核对的不靠人工。** 链接、命令入口、测试登记、行数、导入方向交给脚本。脚本查不到的事实准确性与术语一致性才留人工核对。
5. **现行与过程分离。** `docs/` 只写当前事实，不写日期，不写“已实现”。带日期的计划、审计、验证快照另设目录归档。
6. **例外必须留痕。** 超限、抑制误报、提高上限都要写明原因、登记日期和对象，由审查者核对。例外不是提限许可。

## 措辞约束

规范条文用祈使句或“必须/应当/可以”，事实用陈述句。不写“我们”“你可以”，不写比喻、营销词和无法核实的程度词。禁用词与改写的唯一来源是仓库的术语对照表，新增禁用词先补表再使用。

## 工作流

### A. 修改前定位

1. 读根 `AGENTS.md` 的仓库布局、修改流程与验证矩阵。
2. 按改动路径读最近的子目录 `AGENTS.md`。
3. 只读任务相关源码与专题文档，不在 `docs/` 全量检索。
4. 检查分支与 `git status --short`，保护未提交改动与未跟踪文件。

### B. 新增或修改文档

1. 查术语表。未收录的概念先补表，再使用。
2. 确认该文档的单一职责。已在别处维护的事实只链接。
3. 按 `references/agents-hierarchy.md` 的骨架写作，`assets/` 下有可复制模板。
4. 在上级目录树与内容分工表登记新文档。
5. 运行格式检查、文档链接检查与阈值检查。

### C. 新增检查或阈值

1. 单一职责的 `check-*.ts` 放 `scripts/gates/`，不合并多个关注点。
2. 接入聚合入口的检查数组，构建排在最后。
3. 在命令清单声明入口，确认路径自查覆盖新脚本。
4. 阈值与例外写配置文件，例外填原因、日期和对象。
5. 补单元测试并登记到测试注册表。细节见 `references/gates-and-tests.md`。

### D. 新增测试

1. 放入已登记的 scope 目录即完成登记，无需逐文件登记。
2. 新目录、新层级或新执行器先改注册表表格，再写文件。
3. 元数据必须有机械证据。例如 `isolated` 对应临时目录创建调用，`snapshot` 对应截图断言，`scene` 对应重型场景标签。证据名称按项目实际调整，双向核对的要求不变。
4. 运行注册表一致性检查。

### E. 在新仓库建立同一套规范

按 `references/adoption.md` 的六阶段顺序推进。先术语与行文，再根入口，再按改动热点补子目录入口，最后加门禁与阈值。一次铺满会产出成批无入口文档。

## 内容放置判定

| 内容                                 | 位置                 |
| ------------------------------------ | -------------------- |
| 跨目录约束、入口、验证矩阵           | 根 `AGENTS.md`       |
| 目录树、文件职责、本地例外、扩展去向 | 该目录 `AGENTS.md`   |
| 现行架构、接口、部署与质量决策       | `docs/architecture/` |
| 术语、缩写、禁用词与改写             | 术语对照表           |
| 翻译与双语对应规则                   | 翻译规则文档         |
| 测试层级、注册表与执行计划           | 测试注册表文档       |
| 采用的架构决策与取舍                 | `docs/adr/`          |
| 带日期的计划、审计、验证快照         | 过程材料目录         |
| 可复用的 Agent 能力                  | 技能目录             |

## 反模式

- 同一事实在根入口、子目录入口和专题文档各写一遍。
- 文档出现“已实现”“即将支持”，或给现行事实标注日期。
- 用营销词或程度词替代具体对象与动作。
- 为通过检查拆文件、调高阈值、加 suppress 或删测试。
- 新增测试文件不登记范围，或声明元数据却没有对应证据。
- 新建第二份命令清单、第二套术语或第二个入口。
- 未经明确要求执行 commit、push、rebase 或修改历史。
- 把现行文档目录当作过程记录仓库。

## 交付前自检

- [ ] 新概念已补术语表，全文只用一个词。
- [ ] 每条事实有源码、配置或脚本输出作依据。
- [ ] 上级目录树与内容分工表已登记新文件。
- [ ] 命令、路径与阈值用链接指向唯一维护处。
- [ ] 对应验证已执行，失败与未覆盖范围如实报告。
- [ ] `git status` 只包含预期改动。

## 常见落地结构

推荐的目录与文件位置，按仓库实际情况调整：

- 根约束、脚本入口与文档写作：根 `AGENTS.md`、`scripts/AGENTS.md`、`docs/AGENTS.md`
- 术语与翻译：`docs/terminology/`
- 质量规则与阈值：`docs/architecture/engineering-quality.md`、阈值配置文件
- 测试注册表：`docs/testing/README.md`、测试计划脚本
- 门禁实现：`scripts/gates/`
- 过程材料：`.agents/notes/`
